This tutorial attaches a GitHub provider whose profile permits clone and fetch,
observes a denied push, and adds an enforced repository-scoped Git Smart HTTP
rule. The GitHub credential remains bound by the provider profile while the
sandbox policy grants the additional network operation.

## Prerequisites

Before you begin, make sure you have:

- A current OpenShell CLI connected to a matching gateway.
- A workload image that contains your agent and Git at `/usr/bin/git`.
- An Anthropic API key with access to a model supported by the Claude Code
  version in that image.
- A GitHub personal access token with permission to push to both repositories.
  The negative test must reach OpenShell's receive-pack boundary instead of
  stopping at GitHub authentication or authorization.
- Two GitHub repositories you own: the target repository and a scratch
  repository used only for the controlled negative test.

The examples use a sandbox named `github-demo`. Replace `<org>`, `<repo>`, and
the image reference with your values.

## Import the Agent and GitHub Profiles

The gateway binary does not embed provider profiles. Download, review, and
import both profiles once per gateway:

```shell
curl -LsSfO https://raw.githubusercontent.com/NVIDIA/OpenShell/main/providers/github.yaml
curl -LsSfO https://raw.githubusercontent.com/NVIDIA/OpenShell/main/providers/claude-code.yaml
openshell profile lint -f github.yaml
openshell profile lint -f claude-code.yaml
openshell profile import -f github.yaml --global
openshell profile import -f claude-code.yaml --global
```

The GitHub profile permits read-only GitHub REST and GraphQL access and Git clone or
fetch. It deliberately omits `git-receive-pack`, the Smart HTTP operation used
for push. Its endpoint definitions also bind the GitHub credential to GitHub.
The Claude Code profile supplies the separate model credential and network
access the agent needs to run.

## Create the Providers and Sandbox

Read both credentials from your host environment and store them in separate
providers:

```shell
export ANTHROPIC_API_KEY=<your-api-key>
export GITHUB_TOKEN=<your-token>
openshell provider create \
  --name my-claude \
  --type claude-code \
  --from-existing
openshell provider create \
  --name my-github \
  --type github \
  --from-existing
```

Create the sandbox and attach both providers. The workload command does not
cause the CLI to infer or attach a model provider:

```shell
openshell sandbox create \
  --name github-demo \
  --from registry.example.com/your-org/claude-agent:latest \
  --provider my-claude \
  --provider my-github \
  -- claude
```

Do not paste either credential into the agent conversation. The sandbox receives
OpenShell placeholders, and the proxy resolves each one only for destinations
covered by its provider's credential boundary.

In another host terminal, confirm the executable path expected by the policy:

```shell
openshell sandbox exec -n github-demo --no-login-shell -- command -v git
```

Continue when the command reports `/usr/bin/git`. If your image uses another
path, use that canonical path in the update commands below and update a custom
copy of the provider profile when its binary list also needs to change.

## Observe the Denied Push

Ask the agent to clone the repository, add a small file, commit it, and push:

```md title="Prompt" wordWrap showLineNumbers={false}
Clone `https://github.com/<org>/<repo>`, add a `hello_world.py` file, commit it,
and push the commit. Do not change credentials or bypass OpenShell policy.
```

Clone and fetch can succeed through the provider-contributed rule. The push is
denied because no effective rule permits `POST
/<org>/<repo>.git/git-receive-pack`.

Inspect recent sandbox events from the host:

```shell
openshell logs github-demo --since 5m --source sandbox
```

Find an OpenShell denial for `github.com:443`, `/usr/bin/git`, method `POST`,
and the target repository's `git-receive-pack` path. A GitHub authentication or
repository-permission error is a different failure and is not fixed by widening
network policy.

## Add a Repository-Scoped Rule

Create a sandbox-authored REST rule for Git. This update preserves the base
filesystem, process, middleware, and provider-derived rules:

```shell
openshell policy update github-demo \
  --rule-name github_push \
  --binary /usr/bin/git \
  --add-endpoint github.com:443:read-only:rest:enforce \
  --wait
```

Append the one write operation needed for the target repository:

```shell
openshell policy update github-demo \
  --rule-name github_push \
  --binary /usr/bin/git \
  --add-allow 'github.com:443:POST:/<org>/<repo>.git/git-receive-pack' \
  --wait
```

The endpoint uses `enforcement: enforce`, so unlisted requests are blocked. The
path permits push only to the named repository. It does not grant pushes to
other repositories, GitHub REST writes, or GraphQL mutations.

Compatible matching rules can contribute permissions. The provider-owned Git
rule continues to permit clone and fetch, while the sandbox-authored rule adds
the selected receive-pack operation. Provider entries remain immutable and do
not appear in the editable base policy.

## Inspect the Effective Change

Inspect the base and effective views:

```shell
openshell policy get github-demo --base
openshell policy get github-demo --full
openshell policy list github-demo
```

The base contains `github_push`. The effective view also contains reserved
provider-contributed rules. A successful `--wait` can report loaded, unchanged,
or superseded state, so confirm the current active revision before retrying.

## Retry and Verify

Ask the agent to retry the same push. It should complete when the token and
repository permissions also allow it.

Then test the denied side of the boundary from the cloned repository. Use the
other disposable scratch repository and a branch name reserved for this test.
This command performs a real push: if the policy is unexpectedly too broad, it
can create the remote branch. Delete that branch outside the sandbox and
investigate the policy before continuing. From a trusted checkout, you can
delete it with `git push https://github.com/<org>/<other-repo>.git
:refs/heads/openshell-policy-negative-test`.

Ask the agent to run:

```md title="Prompt" wordWrap showLineNumbers={false}
From the cloned repository, run this command once without changing a remote or
retrying with different credentials. The destination is a disposable scratch
repository:

git push https://github.com/<org>/<other-repo>.git HEAD:refs/heads/openshell-policy-negative-test
```

OpenShell must deny the `POST
/<org>/<other-repo>.git/git-receive-pack` request before Git completes that
push. Use Git rather than `curl` because the rule selects `/usr/bin/git`.
Reviewing `policy update --dry-run` would only inspect a merged configuration
and would not test runtime denial.

Inspect the events again:

```shell
openshell logs github-demo --since 5m --source sandbox
```

Confirm a new denial event names the other repository's `git-receive-pack`
path. An earlier denial or an event for the intended repository does not prove
this test was blocked. Also confirm the allowed request targets the intended
repository and that no broader GitHub write rule was added.

## Remove Push Access

Remove the sandbox-authored rule when the task no longer requires push:

```shell
openshell policy update github-demo \
  --remove-rule github_push \
  --wait
```

Clone and fetch remain available through the attached provider profile, while
push returns to denied.

## Clean Up

Delete the sandbox and provider when you finish:

```shell
openshell sandbox delete github-demo
openshell provider delete my-claude my-github
```
