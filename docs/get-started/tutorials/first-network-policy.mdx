This tutorial creates a sandbox with known tools, shows an OpenShell network
denial, and adds an enforced rule that permits HTTP reads but denies writes.
Every command runs from your host terminal.

## Prerequisites

Before you begin, make sure you have:

- A current OpenShell CLI connected to a matching local gateway that uses the
  Docker compute driver.
- Docker on the host.
- An isolated tutorial gateway with no gateway-global policy.

The tutorial creates the sandbox without providers and inspects its effective
policy. Do not use a shared gateway where an existing global policy or automated
operator may change the sandbox during the exercise.

<Tip>
The repository includes an optional automated version of this tutorial in
[`examples/sandbox-policy-quickstart`](https://github.com/NVIDIA/OpenShell/tree/main/examples/sandbox-policy-quickstart).
The automated script also requires `jq` on the host. From a source checkout, run
`bash examples/sandbox-policy-quickstart/demo.sh`. The script builds the image,
creates one sandbox, exercises deny, allow, and deny again, and removes only the
sandbox and temporary policy export it created. It leaves the local image in
place.
</Tip>

## Prepare the Tutorial Sandbox

If you still need to install the CLI or configure a gateway, complete the
[Quickstart](/get-started/quickstart) first.

Create an empty directory, download the maintained example Dockerfile, and
review it before building:

```shell
mkdir openshell-policy-quickstart
cd openshell-policy-quickstart
curl -LsSfO https://raw.githubusercontent.com/NVIDIA/OpenShell/main/examples/sandbox-policy-quickstart/Dockerfile
sed -n '1,200p' Dockerfile
```

Build the image so the sandbox has `/usr/bin/curl` and CA certificates:

```shell
docker build -t openshell-policy-quickstart:0.1 .
```

For a Podman gateway, build a Podman-visible image instead and follow the driver
notes in [Manage Sandboxes](/sandboxes/manage-sandboxes#sandbox-images).
For a remote gateway, push the image to a registry the gateway can pull from and
replace the image reference below.

Create `demo` with no automatically attached providers. The sleep command keeps
the sandbox running while you try requests from your host terminal. `--detach`
returns control to that terminal:

```shell
openshell sandbox create \
  --name demo \
  --from openshell-policy-quickstart:0.1 \
  --no-auto-providers \
  --no-tty \
  --detach \
  -- /usr/bin/sleep infinity
```

Inspect the effective policy before treating the sandbox as default-deny:

```shell
openshell policy get demo --full
```

In the displayed YAML, check that `network_policies` is absent or empty before
continuing. OpenShell omits the section when there are no network rules.
`--no-auto-providers` avoids provider attachment, but it does not override a
gateway-global policy or an embedded image policy.

Confirm the image contains the expected executable and trust store:

```shell
openshell sandbox exec -n demo --no-login-shell -- test -x /usr/bin/curl
openshell sandbox exec -n demo --no-login-shell -- \
  test -r /etc/ssl/certs/ca-certificates.crt
```

## Observe Default-Deny Networking

Request an unauthenticated GitHub REST endpoint:

```shell
openshell sandbox exec -n demo --no-login-shell -- \
  /usr/bin/curl --silent --show-error --fail --max-time 10 \
  https://api.github.com/zen
```

The command fails because no network rule permits `/usr/bin/curl` to connect to
`api.github.com:443`. Curl can surface this as `Could not resolve host` because
policy DNS refuses names with no eligible network rule. A DNS error alone does
not tell you why the request failed. Look for the matching OpenShell event below
to confirm that policy blocked it.

Inspect the sandbox's structured events. OCSF policy events use the INFO tracing
level even when the event itself describes a denial:

```shell
openshell logs demo --since 5m --source sandbox
```

Find the `NET:REFUSE` event for `api.github.com:53` with reason
`policy_dns_ineligible`. It confirms that OpenShell refused name resolution
because no network policy made the destination eligible. A missing executable,
unrelated DNS failure, or TLS trust error has a different cause.

## Add an Enforced Read-Only Rule

Use an incremental update for the network grant. This leaves the sandbox's
filesystem, Landlock, and process settings unchanged:

```shell
openshell policy update demo \
  --rule-name github_readonly \
  --binary /usr/bin/curl \
  --add-endpoint api.github.com:443:read-only:rest:enforce \
  --wait
```

The rule selects one destination and one executable. `protocol: rest` enables
HTTP request inspection, `read-only` permits the REST methods GET, HEAD, and
OPTIONS, and `enforce` blocks requests outside that set. Omitting enforcement
would select audit mode, which logs an applicable violation but forwards the
request.

Check the revision after `--wait` returns:

```shell
openshell policy list demo
```

A successful wait can also report an unchanged or superseded revision. Confirm
which revision is active before relying on the new permission.

## Verify the Allowed and Denied Requests

Repeat the GET request:

```shell
openshell sandbox exec -n demo --no-login-shell -- \
  /usr/bin/curl --silent --show-error --fail --max-time 15 \
  https://api.github.com/zen
```

The request now returns text from the GitHub API.

Send a POST to the same endpoint:

```shell
openshell sandbox exec -n demo --no-login-shell -- \
  /usr/bin/curl --silent --show-error --max-time 15 \
  --request POST https://api.github.com/zen
```

OpenShell returns an HTTP 403 response containing `policy_denied`. An upstream
403, 404, or rate-limit response does not demonstrate policy enforcement. The
`read-only` preset controls HTTP methods; the API determines what those methods
do.

Inspect the request denial:

```shell
openshell logs demo --since 5m --source sandbox
```

The event identifies the REST action, destination, policy, and denial reason.

## Remove the Rule

Delete the named network rule and wait for the new revision:

```shell
openshell policy update demo \
  --remove-rule github_readonly \
  --wait
```

Run the GET again. It fails at the connection boundary because the sandbox has
returned to its original network policy:

```shell
openshell sandbox exec -n demo --no-login-shell -- \
  /usr/bin/curl --silent --show-error --fail --max-time 10 \
  https://api.github.com/zen
```

## Clean Up

Delete the sandbox when you finish:

```shell
openshell sandbox delete demo
```
